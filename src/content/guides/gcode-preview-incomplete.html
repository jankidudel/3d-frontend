A G-code preview is usually incomplete for one of five reasons: the file uses commands the viewer does not draw (arcs, offsets or macros), it is larger than the preview limit, it is a binary or vendor-specific file, it has a broken line, or it contains no moves at all. Each needs a different fix. Check what the viewer says about each result rather than judging by the picture alone.

A real example: we opened an unedited PrusaSlicer export, R1.gcode, in the live InspectMesh viewer on 1 November 2026 (see the saved review, file SHA-256 969076ce46221073a30ba87f32f5bba6e9c032baf1315dd11351307a83faa101). The moves and extrusion were marked incomplete, the print time and filament amount were read correctly, and all 4,796 lines were reviewed. Commands the viewer does not follow included G28 (homing) and M84 (motors off).

Jump from a finding to the line that caused it

Our arc example starts with ordinary straight moves, then uses a G2 arc and a custom macro. InspectMesh groups the commands it cannot follow, shows the first and last line numbers with up to three sample lines, and marks the moves after them as incomplete. Clicking a sample shows it in a read-only panel. Only a movement line it could place selects a preview layer; other lines have no exact layer.

Find the cause before changing the file

Cause What it means What to do
G2/G3 arc, offset, unsupported macro or tool change Moves and size range are incomplete after that point Check the preview in your slicer and your firmware's documentation
Too many moves to draw Only the first 50,000 moves are drawn; size ranges still use all straight moves Use your slicer's preview for the full picture
Too many lines Only the first 200,000 lines are read; later moves and information may be missing Use your slicer's analysis; note the partial-read warning
Binary or vendor file Not supported: only plain-text .gcode, .gco and .gc Open it in the program that made it, or export plain text
Broken or invalid number Import stops at that line Check the original export and export again; don't guess a fix
Empty or comments only No G0/G1 moves to show Make sure you have the right sliced file

Renaming a file does not convert it

Renaming a binary file to .gcode does not make it readable text. Prusa documents its own binary G-code format, which PrusaSlicer can view and convert; InspectMesh cannot read it or other vendor formats. Files with unreadable bytes or control characters are rejected. Files can be up to 25 MiB, and lines longer than 4,096 characters are skipped.

What can still be trusted?

A print time written by PrusaSlicer 2.9.6 (normal mode) can still be read even if an arc makes the size range incomplete. It is the slicer's estimate, not a measured time, and does not mean every move was checked. A filament amount that is missing or unclear stays blank, never zero. Amounts for several tools are not merged into one spool, and a filament length needs a confirmed diameter and density before converting to weight.

Mode commands matter too. Switching G90/G91 after M82/M83 can change how extrusion is read depending on firmware, so InspectMesh flags it. G92 E resets the extrusion counter without moving; G92 X/Y/Z changes the coordinate reference, so the size range no longer matches the real bed. M82 combined with relative X/Y/Z is also flagged. See absolute vs relative extrusion for worked examples.

Reading an F (feed rate) value is not a time simulation; see G-code feed rate. Information that is not in the file stays blank.
