What G-code contains

A typical 3D-printing G-code file contains a mixture of:

  • movement instructions for the print head;
  • extrusion and travel moves;
  • layer changes;
  • hotend and bed temperature commands;
  • homing and setup commands;
  • comments written by the slicer;
  • printer-specific start and end sequences.

The exact format is not identical across every slicer or printer firmware. Two files that both end in .gcode can contain different comments, custom commands and coordinate conventions.

That is why a useful checker should explain what it recognised and what it could not interpret.

Check the file before sending it to the printer

The G-code Preflight Checker can help you review:

  • file size and readable slicer metadata;
  • estimated print time when the slicer provides it;
  • declared filament use when available;
  • parsed layer count and Z range;
  • parsed X/Y/Z toolpath extents;
  • common hotend and bed temperature targets;
  • coordinate and extrusion modes;
  • unsupported commands that limit analysis.

Preserve the exact output and compare unsupported scope with the generating slicer, especially when the file came from someone else or was modified.

Compare toolpath size with your printer

A model can fit your printer in CAD and still produce unexpected G-code if the wrong printer profile, scale or coordinate setup was used during slicing.

The toolpath extents in G-code show the range of movement the parser found. Compare them with the usable dimensions of the intended printer.

If the parsed extents exceed the build volume you entered, stop and check the slicer profile before printing.

An in-bounds result is still not a guarantee. Start G-code, coordinate offsets, purge routines and printer-specific behaviour can affect how the machine uses its build area.

For the earlier model-level check, use the STL Dimensions Checker or 3MF Dimensions Checker.

Check temperature targets without judging them in isolation

G-code commonly includes commands that set hotend and bed targets. The checker can show the temperatures it finds, including commands that wait for a target before continuing.

That is useful for catching obvious surprises, such as loading a file intended for a different material profile.

But a temperature number is not enough to judge a print. The correct setting depends on the material, printer, nozzle, enclosure, cooling and manufacturer guidance. Do not edit a G-code file merely because a generic checker displays a value you did not expect.

Surprising solid/dashed classification needs the preceding M82/M83 and G92 state. A surprising F1800 needs feed-rate units and modal interpretation. Neither the last E coordinate nor an F value supplies complete consumption or elapsed duration.

Read coverage before relying on a path picture

Review linear, extrusion, duration and material coverage separately. Unsupported arcs, macros, tool or coordinate effects can leave a picture incomplete without invalidating a supported declared duration. Follow the finding's original source line and the coverage owner; do not infer compatibility from recognised-line counts.

G-code checking comes after model preflight

A clean G-code file does not prove that the original model was well prepared.

Before slicing, inspect the model itself:

  1. use STL Print Preflight or 3MF Print Preflight;
  2. confirm dimensions, printer fit and mesh health;
  3. review wall thickness and overhang risk where relevant;
  4. choose orientation, supports and material settings in the slicer;
  5. inspect the finished G-code before printing.

This sequence catches problems at the stage where they are easiest to understand and correct.

Use the embedded time estimate as an estimate

The supported G-code parser reads declared slicer metadata where present; it does not recreate a printer's motion planner. A sliced-file duration has more job context than an STL volume, yet acceleration, firmware limits, warm-up and pauses can still make real elapsed time differ.

Illustrative observation: the slicer says 5 hours and a comparable completed job took 6 hours. An observed correction factor is 6 / 5 = 1.2. A later 4-hour estimate becomes 4.8 hours before any separately omitted setup allowance. One observation is weak evidence; track comparable jobs and avoid transferring a factor from a small detailed part to a large continuous extrusion.

Plan the finish instant in your chosen timezone. That tool adds elapsed duration across midnight and daylight-saving boundaries, accepts supported duration metadata and leaves it editable. It does not monitor the printer, send reminders or know when a job actually finishes. Keep safety and running-printer decisions with the printer's operating guidance.

Geometry preflight reviews the source mesh; G-code review examines the sliced job. Neither simulates all firmware behaviour or certifies printer safety. When a relevant command cannot be interpreted, stop and use the generating slicer and printer documentation.

Use source evidence to choose the next action

Read the viewer's linear, extrusion, duration and material coverage before interpreting extents. Expand Source-line evidence, select the finding's original line and inspect the read-only excerpt. Repeated events include first/last references and a total; a bounded sample is not the entire source. Only a mapped retained motion line selects a preview layer. Mode, temperature and metadata lines should not be assigned an invented layer.

An arc or macro points to incomplete preview review; unexpected coordinate location points to min/max and travel review. For a supported estimate, review its source, units, one-run scope and any manual edit before offering it. The destination asks before applying, and cost adds a new selected run rather than multiplying every plate. Copy, JSON, PDF and print keep the same assumptions and warnings. A local byte hash identifies exact bytes, not the slicer author.
