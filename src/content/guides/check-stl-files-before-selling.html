Before distributing a collection, record what each file is intended to represent, its assumed dimensions and the checks actually completed. A clean mesh screen is useful evidence, but it does not justify promising that every customer printer or slicer will print the model successfully.

Use a collection report with independent outcomes

Run the built-in mixed collection. The closed cube has known 20 mm dimensions and screened 8,000 mm³ volume; the open-face cube has four boundary edges and unavailable volume; malformed input fails separately. This is the behaviour a review process needs: one failed file cannot be hidden by a collection-wide green badge.

Handoff field What to record
Dimensions Expected size and explicit STL unit assumption
Geometry Boundary, non-manifold, duplicate, degenerate and winding findings
Shells Whether separate shells are intentional separate parts
Sampling Wall threshold, sample count and unmeasured locations
Limitations Unchecked self intersections, slicer settings and physical behaviour

Separate a mesh finding from a process promise

An intentional open surface may be an authoring intermediate, while a downloadable solid part should receive the intended solid interpretation. A multi-shell model can be several legitimate pieces. State the intended task so the next reviewer knows which finding requires correction. The checker cannot infer that design intent.

Do not translate “no issue found in completed checks” into guaranteed printability. Supports, shrinkage, nozzle profile, material formulation and real-world assembly are separate decisions. If you have no physical-print evidence, identify the file examples and screenshots as software demonstrations.

Review replacement exports consistently

Keep revisions separately and use surface comparison after cleanup. Exported triangles can change without changing shape; the unchanged retriangulation control helps distinguish that case. Record any alignment and tolerance rather than choosing a hidden normalisation.

Export JSON for full settings and CSV for a collection summary, then store your release notes with the files. Optional browser-local report history is convenient but can disappear when browser data is cleared. Export anything you need to retain. This checklist concerns technical handoff and provides no licensing or legal advice.

Give the next reviewer an actionable note

Example handoff: “The closed cube completed topology checks at an assumed millimetre scale; its dimensions are 20 mm on every axis. The open-face control has four boundary edges, so its volume is unavailable. Printer fit was skipped because no profile was selected.” This records what actually ran and one decision still required. It is more useful than labelling every exported file passed.
